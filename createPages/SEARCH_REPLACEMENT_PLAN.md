# Bible search replacement plan

Date: 1 November 2026

Status: The native replacement is implemented. Local qualification and remaining release work are recorded in [SEARCH_QUALIFICATION.md](SEARCH_QUALIFICATION.md). Production deployment and its observation period have not been performed. Step 11 remains a set of follow-up extensions; original-word identifiers and exact source morphology codes are already supported.

Replace Pagefind with search data generated by OBD and a browser search engine maintained in this repository. Keep static hosting and the existing `Search.htm` address. Readers should be able to find a passage, search particular translations and books, and distinguish Bible text from notes and reference material.

The basic searchable unit is a passage in one source version, normally a native verse. Search that unit once regardless of how many chapter, section, book, parallel, or interlinear pages display it. Preserve the source numbering and use verified mappings for cross-version navigation and grouping.

## Experience and release scope

The first replacement release should provide:

- Reference lookup with book-name suggestions, abbreviations, chapters, verses, ranges, and version selection.
- Bible text searches for all words, any word, and exact phrases, plus excluded words and whole-word matching.
- Filters for available versions, language, books, OT, NT, additional books, and a reference range. Keep the selected scope visible.
- Original-script and transliteration searches, with clear choices about accents and Hebrew pointing.
- Separately labelled searches of the notes, headings, and supplementary text currently discoverable through indexed OET and parallel pages.
- Results containing the source reference, version, highlighted text, and verified links to context and study views.
- Shareable search URLs, browser Back/Forward support, accessible keyboard controls, and usable mobile layouts.

Default to OET-RV for a visit without a version preference, with obvious OET-LV, both OET versions, and other-version choices. A search opened from a Bible page should carry its version and offer its current book as a scope. Do not silently restrict every new search to that book. The combined OET choice searches RV and LV separately and identifies which text matched.

Lemma, morphology, related-word, and broader topic searches follow after the basic replacement has been verified. The index format should accommodate their identifiers from the beginning.

## Ideas from STEP Bible

STEP Bible links to a guide describing a single input with suggestions for passages, resources, text, original words, and subjects. Its advanced forms expose all/any/phrase matching, prefixes, exclusions, and nearby-verse conditions. These are useful patterns for OBD, especially making complex searches possible through ordinary controls. See [Finding Words, Verses, and Subjects](https://stepbibleguide.blogspot.com/p/finding.html) and [Using Advanced Search](https://stepbibleguide.blogspot.com/p/advanced-search.html).

| Pattern to adapt | OBD behaviour | Delivery |
| --- | --- | --- |
| Suggestions distinguish kinds of lookup | Offer “Open passage”, “Find these words”, or an original-word choice without guessing away ambiguous input. | First release |
| Visible resource and passage scope | Show selected versions and book/range filters beside the query; make them easy to clear. | First release |
| Guided text matching | Expose all words, any word, exact phrase, and exclusions without requiring a query language. | First release |
| Original-word selection | Show script, transliteration, lemma, gloss, and source before starting an occurrence search. | Later extension |
| Nearby-verse searches | Let readers explicitly widen matching to adjacent verses in one version. | Later extension |
| Separate subject discovery | Search OBD topic and entity resources, explaining which resource supplied the association. | Later extension |

For OBD, word proximity, result counts by book, copyable reference lists, and a text-versus-lemma distinction would also be valuable. They should be added without making the initial screen require specialist knowledge. STEP provides feature ideas; this plan uses OBD's own data and architecture.

## Step 1 Establish coverage and acceptance examples

Inventory what the current search actually exposes. `_createSearchPage()` uses the standard Pagefind UI, and the build suggests indexing `{OET,par}/**/*.{htm}`. Treat this as a starting scope, then check representative generated pages and search results for Bible text, notes, headings, transliterations, modernised spelling, and substituted translations.

Record coverage by version, language, book, and content type. Include selected-verse editions and versions that have only parallel-page destinations. Separate resources loaded for internal processing from content actually published in this build. Check current build settings rather than relying on the historical test-book list.

Create a small, hand-checked acceptance set: a reference, a common word, an uncommon word, a phrase, a phrase with repeated words, an accented Greek word, pointed Hebrew, a transliteration, a note-only term, and a match in a selected-verse edition. Include multi-version searches where different terms occur only in different translations; those must not become one all-words match.

Capture current search timings and transfer sizes for comparison. Pagefind results are useful coverage evidence, but expected correctness must come from the source text and agreed matching rules.

**Completion:** A documented coverage inventory, expected results for representative queries, and a baseline for build time, index size, network transfer, and browser memory.

## Step 2 Define the search record and publication contract

Use a versioned record schema with these fields:

| Field | Purpose |
| --- | --- |
| Stable source key | Version, content kind, native book/reference or resource identifier, and an ordinal where needed. |
| Native reference | Source versification, book identity, chapter, verse labels, suffixes, and bridge or range membership. |
| Searchable fields | Bible text, headings, notes, transliteration, modernised text, and other displayed derived text kept distinct. |
| Display text and token offsets | Preserve original spelling and reliable highlighting after search normalization. |
| Language and capabilities | Identify available scripts, transformations, lexical annotations, and partial coverage. |
| Destination links | Actual page and anchor links for reading context, parallel, interlinear, and lexical views where available. |
| Optional mapped references | Exact correspondence established by BOS, including complete groups and mapping status. |
| Optional word annotations | Source word IDs, lemma IDs, Strong's identifiers, and morphology with their source scheme. |

Assign compact numeric document IDs within each build for index storage. Keep stable source keys separate from those IDs; URLs and caches must not depend on an ID surviving a rebuild.

Do not expand a stored verse bridge into duplicate text records or invent word boundaries between its members. Describe a bridge match with the bridge's own label. Preserve Psalm headings, verse zero, suffixes, additional books, and source-specific book layouts. Do not assume every edition has the same books or verse count.

Maintain an inventory of published destinations and capabilities. Resolve routes through `navigation.py`, `bibleNavigation.py`, `referencePassages.py`, and `versification.py`, then confirm availability in the actual output. A version without its own chapter pages can use its verified parallel-page anchor. A missing mapping must not hide an otherwise valid native result or create an unchanged-reference fallback.

**Completion:** Schema fixtures cover ordinary verses, bridges, split mappings, additional books, selected verses, notes, unavailable mappings, and partial builds.

## Step 3 Extract searchable text from the source resources

Add a dedicated exporter using the already loaded Bible resources and parsed USFM/ESFM entries. Walk native stored passages once per version. Reuse existing text transformations where appropriate and preserve word-table identifiers; avoid crawling every generated page or stripping raw markup with a broad regular expression.

Export body text separately from headings, notes, cross-reference labels, and derived displays. Keep currently searchable transliterations, modernised spellings, and substituted translations as labelled fields with links to their actual displayed context. Exclude navigation, page furniture, duplicate renderings, and messages such as “Same as above”. A note match must never be described as a Bible-text match.

For study material, have the owning generators emit bounded search records from their parsed content. Each worker writes its own intermediate file; the parent merges files after workers finish. Do not rely on mutations to shared Python state becoming visible across forked workers.

Define normalization explicitly:

- Preserve display text and a map from search tokens to original text spans.
- Specify Unicode normalization, case handling, apostrophes, hyphens, punctuation, and word boundaries. Match complete tokens by default.
- Support accent-insensitive Greek and optional Hebrew vowel/cantillation handling without removing meaningful letters. Offer stricter matching when requested.
- Keep transliteration as an explicit field and show when it supplied the match.
- Keep common words in the positional index so phrases containing words such as “to”, “be”, and “the” remain searchable.
- Keep stemming, spelling modernization, and lemma matching distinct. Do not silently turn an exact-word query into any of these modes.
- Apply all-words and phrase conditions within one field of one source record by default; do not assemble a match from body text, a footnote, and a translation.

Specify what “exact phrase” means: consecutive word tokens in order under the selected case/accent rules, with documented punctuation handling. It is not a promise of byte-for-byte typography.

Use shared conformance examples for the build code and JavaScript query normalizer, including Greek sigma and combining marks. Build-time Python case folding and browser lowercasing must not silently disagree. Specify the units of stored text offsets and their conversion to JavaScript string positions; Unicode code points, UTF-8 bytes, and UTF-16 code units are not interchangeable.

**Completion:** Extracted text and highlights match representative rendered passages, and every omission or malformed record reports its version, native reference, field, and reason.

## Step 4 Build reference lookup independently of text search

Generate a small book-name and alias catalogue from BOS and OBD naming/navigation data. Add tested common English abbreviations, numbered-book variants, and OET names. Export available chapter/verse information and destination mappings in bounded per-version/book files, so reference lookup does not require a text index download.

Support inputs such as `John 3:16`, `Jn 3.16`, `1 Cor 13`, `John 3:16-18`, and comma/semicolon lists. Treat references as belonging to the selected version's numbering unless the reader explicitly selects the shared navigation numbering. Handle single-chapter books explicitly and show choices for ambiguous names such as `John` without a chapter or verse.

Distinguish invalid references, passages absent from a partial edition, books omitted from a test build, and unavailable cross-version mappings. Show useful messages instead of sending readers to a version index without explanation.

**Completion:** Reference tests cover aliases, ranges, suffixes, bridges, single-chapter books, Psalms, additional books, numbering differences, and actual files and anchors. Reference lookup remains usable if the larger text index fails to load.

## Step 5 Generate compact indexes in bounded batches

Create an inverted index: each term points to the source records and token positions where it occurs. Positions support phrases immediately and proximity later. Keep source fields separate throughout the index.

Partition by version and language, with term buckets and book/group partitions where measurements justify them. Provide small catalogues identifying which files a query needs. Store display records in bounded blocks so the first results do not require one request per verse or the entire Bible text.

Start with an inspectable development representation and benchmark a compact, delta-encoded representation for production postings. Choose the final layout using full-corpus measurements, especially for common words and all-version searches. Avoid both one giant JSON index and a vast collection of tiny files.

Build and release one version/book batch at a time. Limit index-worker concurrency separately from page-generation concurrency and release temporary buffers before moving on. Use Python for extraction and orchestration; place measured indexing or encoding bottlenecks in the existing Rust extension. Do not require a browser WASM toolchain unless measurements show it is necessary.

Produce a manifest containing format and normalization versions, content fingerprints, coverage, file locations, sizes, and build identity. Hash inputs including source content, derived-text rules, versification data, selected books, publication settings, and extraction code. Reuse only compatible unchanged artifacts and remove deleted-source entries from the next manifest.

Make output deterministic for identical inputs. Keep build timestamps outside content hashes. Ensure compression and decoding work with the actual static host; do not assume it will serve `.gz` files with appropriate headers without checking.

**Completion:** Repeated builds produce equivalent results, changed and removed sources invalidate the correct artifacts, and bounded-memory generation succeeds on representative large versions.

## Step 6 Implement the browser search engine

Run query work in a Web Worker. Use ordinary JavaScript with a documented index decoder and query format, without introducing another search-library dependency.

Resolve scope before fetching index pieces. Intersect postings for all-words searches, union them for any-word searches, apply exclusions within the chosen scope, and check positions for phrases. Keep an independent straightforward matcher over small fixtures as a correctness reference for the optimized engine.

Load result text only for the visible result page. Bound the cache, cancel superseded requests, ignore late responses from previous queries, and fetch selected versions with limited concurrency. Report loading and failure states explicitly. Never show a partial multi-version result count as complete, or treat a failed download as “No matches”.

Use deterministic book/chapter/verse ordering for Bible results, following the selected OET or traditional order. Offer grouping by passage only for complete, exact mappings. Retain distinct version matches and count source matches separately from grouped passages and word occurrences. Do not infer identical meanings from identical spellings or shared Strong's numbers.

Render excerpts as text with controlled highlight elements. Validate manifest-provided local destinations. Preserve mixed Hebrew/English directionality and highlights spanning combining characters.

**Completion:** Browser results agree with the reference matcher, counts and pagination remain stable, and rapid typing, cancelled work, failed downloads, and large common-word searches do not freeze the interface.

## Step 7 Replace the search interface

Implement the new page at the existing `Search.htm` route. Use one main input with clear modes for Passage, Bible text, and Study material; add Original words when its data is ready. Keep advanced controls collapsed initially.

Show active versions and book/range limits prominently, with a clear reset. Display scope and matching rules in a short sentence, for example “All these words in the same verse · OET-RV · John”. Distinguish a reference suggestion from a text-search suggestion before navigation.

Each Bible result should include the source reference, version, a readable excerpt or verse, highlighted matches, and context links. Keep adjacent context expandable so isolated verses do not become the only reading experience. For grouped results, show exactly which translations matched; neighbouring translations are context, not additional matches.

Encode query, mode, filters, matching options, ordering, and result page in the URL. Restore them on Back/Forward and return from a passage. Carry version context from existing Search links where available. Offer copyable references with version attribution.

Use OBD's colours and theme, visible focus, labelled controls, keyboard-operable suggestions, screen-reader status messages, responsive layouts, and proper bidirectional text. Provide a useful no-JavaScript explanation with ordinary book/version navigation links. If workers are unavailable, retain reference navigation and clearly explain text-search availability.

**Completion:** Representative desktop and phone flows work with keyboard and touch, search links reopen the same query, and loading, empty, ambiguous, and error states are understandable.

## Step 8 Integrate indexing and publication into the build

Add explicit search settings to `State` for enabled content and resource limits. Generate search data under `state.TEMP_BUILD_FOLDER`, respecting the configured destination and all relevant build selectors. Keep `TEST_MODE_FLAG` unchanged during implementation.

The current orchestration loads Bibles and OET word tables, prepares section data, generates page families, calls `_createSearchPage()`, then sets `state.preloadedBibles = None`. Run the bounded Bible export while these resources are still available, after page availability is known and before that release. Merge any per-generator study records and finish the manifest before writing the new search page.

Stage the search scripts, styles, worker, catalogues, records, and indexes with the generated output. Use `search/` for generated search data, extend file-copy and cleanup handling for this directory, and reserve its name in `privateConfig.py`. Include `Search.css` in the existing stylesheet validation workflow.

Handle these build cases explicitly:

- Test builds and `TEST_VERSIONS_ONLY` advertise only their published content and remain separate from production indexes and caches.
- `CREATE_BOOK_AND_OTHER_PAGES_FLAG`, parallel-page settings, and selected-verse sources determine which destinations are valid.
- `REUSE_EXISTING_WORD_PAGES_FLAG` reuses compatible study-search records with their pages, or rebuilds those records from the matching source; never joins a new index to incompatible retained pages.
- Private-build sources follow the same destination isolation as private pages. Only content selected for that build enters its manifest.
- Resource-pickle freshness and search-cache freshness use explicit fingerprints. A valid old search cache must not disguise a changed source or extractor.

Once the native search is enabled for release, index generation or validation failure must stop publication. Keep the previously published search usable until its successor is complete.

The current site publication deletes and moves output; it is not an atomic site deployment. Give search immutable filenames and publish its manifest pointer after all referenced assets and target pages are ready. Adjust cleanup to preserve the currently served search page and index generation until their replacements are installed. Replace the manifest pointer and search page through temporary files and same-filesystem renames, with a compatibility check between the page and manifest. Retain the previous search generation for a defined cache-grace period and provide a reload message for an incompatible cached client. This protects search assets without making the entire site's publication atomic. Test interrupted publication and rollback before switching the default page.

**Completion:** One ordinary build produces working search without a separate command. Failed, partial, private, reused-resource, and interrupted-publication cases cannot silently replace production search with incomplete data.

## Step 9 Verify correctness and performance at production scale

Run focused unittest scripts from `createPages/` with `uv run`, relevant existing navigation and versification tests, and Rust tests if Rust changes. Discover the current test inventory rather than relying on an old test count. Add browser checks for behaviour that cannot be established by Python or Rust tests.

| Area | Required checks |
| --- | --- |
| Text matching | Whole words, repeated words, phrases, exclusions, punctuation, accents, common words, and no cross-version or cross-field false matches. |
| Passage identity | Bridges, verse zero, suffixes, single-chapter books, additional books, split/combined mappings, missing mappings, and partial editions. |
| Derived content | Transliteration, modernised text, substituted translations, and note-only matches retain accurate labels and destinations. |
| Destinations | Every emitted route comes from the output inventory; validate files and anchors, including versions without chapter pages and reused resources. |
| Build lifecycle | Cache hits, changed sources, deletions, format changes, restricted builds, absent search files, interruption, rollback, and mixed cached generations. |
| Browser behaviour | Mobile layout, RTL text, keyboard/screen-reader flows, Back/Forward, shared links, cancellation, pagination, and explicit partial/error states. |
| Scale | Default OET search, one large version, several versions, all versions, common terms, long queries, and cold versus warm caches. |

Before cutover, measure full-corpus indexes in an isolated search-only build or staging output. Do not infer production performance from a few test books or change the production build flags casually.

Use these as initial engineering targets, to be confirmed against the baseline: default OET searches should show their first result page within three seconds on a cold cache at 10 Mbit/s and 100 ms latency, and warm searches within 250 ms at the 95th percentile on a representative phone. Measure worker memory, total transferred bytes, request count, and added build time/peak memory as well as latency. Set separate explicit budgets for all-version searches after the corpus inventory; show progress while those searches complete.

If a budget is missed, adjust partitioning, encoding, caching, or concurrency and remeasure. Do not silently discard common words, versions, or results to reach a speed target.

**Completion:** The acceptance set passes, coverage differences from Pagefind are explained, full-scale measurements are recorded, and the release has no unresolved correctness or publication failures.

## Step 10 Switch over and remove Pagefind

Keep the existing search as a temporary comparison path during development. Switch `Search.htm` to the native engine only after Step 9 passes. Keep a complete previous deployment available for rollback during the initial production observation period.

Remove these dependencies and references from active code:

1. `PagefindUI`, Pagefind script/style includes, and attribution in `_createSearchPage()`.
2. The printed `npx pagefind` instruction at the end of the build.
3. Pagefind-specific stylesheet-path handling in `html.py` and `Rust/src/missing_styles.rs`.
4. Active documentation telling maintainers to run Pagefind or attributing the new search to it.
5. Any actual deployment scripts or package entries found during the inventory; do not assume these exist in the repository.

Review the reserved `pagefind` folder name in `privateConfig.py` as a migration concern: retain it while old deployment directories exist, then retire it when safe. Remove obsolete deployed Pagefind assets only after old clients and the rollback window no longer need them. Historical changelog entries and this migration plan can remain.

Build into a fresh output directory with no Pagefind assets or installation, run the acceptance searches, and inspect browser network requests. Confirm that no Pagefind code is imported and that search is complete at the end of the normal build.

**Completion:** Production search and new builds work without Pagefind, documented build instructions require no post-build indexing, and the migration/rollback observation period is complete.

## Step 11 Extend Bible study searches

Add these as independently verifiable follow-up changes:

1. **Original words:** Reuse `lexicalLinks.py` and `referenceOccurrences.py` for lemma, form, and Strong's searches. Preserve extended identifiers, Hebrew morpheme alignment, and the distinction between Hebrew and Aramaic. Show annotation coverage and source text; do not imply that every translation has aligned word annotations.
2. **Morphology:** Provide labelled grammatical filters for supported sources, translating source-specific morphology codes through documented mappings. Display unknown or unsupported capabilities explicitly.
3. **Proximity:** Add ordered/unordered word distance and an explicit adjacent-verse scope. Define distance and boundaries, including verse bridges and chapter boundaries, and never join different versions into one match.
4. **Topics and entities:** Search existing topic, person, place, dictionary, and grammar resources through their structured identifiers and associations. Keep supplied topical links separate from text occurrences and lexical similarity.
5. **Exploration tools:** Add counts by book, copy/download of reference lists, optional prefix matching, and carefully bounded spelling suggestions. Label suggestions rather than silently rewriting the query.

These extensions are not prerequisites for removing Pagefind. Natural-language semantic search, generated answers, and a server search service are outside this replacement plan.
